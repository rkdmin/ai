# 0009 — 분석 결과 정합성

## 배경

분석 응답의 세 필드(`faceType` / `features` / `moodArchetype`)가 서로 독립적으로 판단되고 있었다.
`ANALYZE_PROMPT` 는 각 필드의 판단 기준만 주고 **필드 사이가 앞뒤 맞아야 한다는 제약을 주지 않았다.**
그 결과 다음이 모두 통과했다.

- 둥근형 + `사각턱` — 둥근형 정의는 "gonial 코너 부드러움"이라 동시에 참일 수 없다
- `눈꼬리 처짐` + `눈꼬리 올라감` — 같은 부위의 반대 속성
- 둥근형 + `SHARP` — `face-hair.json` 이 얼굴형별 무드 후보를 이미 갖고 있는데도

무드가 특히 허술했다. 헤어 컨텍스트는 후보를 나열만 하고, 프롬프트 후반의 moodLabel 규칙이
다시 "8개 중 하나"로 열어버려 후보 제약을 무력화했다. 메이크업·종합 카드에는 후보가 아예
전달되지 않았다. 분석 단계의 `moodArchetype` 도 카드 프롬프트로 넘어가지 않아,
`mappers.buildMoodBoard` 가 카드 무드와 분석 무드를 병합할 때 상반된 키워드가 나란히 떴다.

모순 해결을 지시하는 문장은 `build_makeup_context` 의 병합 규칙 한 줄뿐이었고, 그것도
"얼굴형 레이어 vs 퍼스널컬러 레이어" 충돌만 다루며 퍼스널컬러를 모르는 사용자에게는 전달조차 되지 않았다.

## 결정

### 1. 정합성 제약을 데이터와 프롬프트 양쪽에 명시한다

- `face-hair.json[].moodBanned` 신설 — 얼굴형과 정면으로 어긋나는 무드 (둥근형 → `SHARP`, `EDGY`).
  선호 무드(`moodArchetype`)와 함께 **얼굴형별 무드의 단일 소스**가 된다.
- `rag_service.CONFLICTING_FEATURES` — 얼굴형별 금지 feature. 근거는 `ANALYZE_PROMPT` 의 형별 정의다.
- `rag_service.EXCLUSIVE_FEATURE_PAIRS` — 같은 부위의 반대 속성 10쌍.
- `ANALYZE_PROMPT` 에 정합성 규칙 섹션과 얼굴형별 선호/금지 무드 표를 주입한다 (표는 JSON 에서 런타임 생성).
- `_build_cards_prompt` 는 이유문 정합성 규칙 + 얼굴형별 허용 무드 + 분석 무드를 함께 넘긴다.

### 2. 충돌 시 features 를 버리는 게 아니라 얼굴형 판정을 되돌아보게 한다

프롬프트는 "상충하는 특징이 확실히 보이면 그 특징을 빼기 전에 얼굴형 판정을 먼저 다시 검토하라"고
지시하고, 재검토 후에도 얼굴형이 맞으면 **얼굴형과 무관한 이목구비 특징에서 대신 채우라**고 한다.
feature 라벨 37개 중 얼굴형과 충돌할 수 있는 것은 6개뿐이고 나머지 31개는 윤곽과 직교하므로,
채울 재료는 충분하다.

### 3. 사후 필터를 마지막 방어선으로 둔다 — 단, 지어내서 채우지 않는다

`sanitize_analysis()` 가 `analyze_face` 응답에서 충돌 항목을 제거한다. 프롬프트 지시는 확률적이라
규칙만으로는 보증이 안 된다.

**비어버린 `features` 는 임의로 채우지 않는다.** 분석하지 않은 특징을 지어내느니 적게 보여주는 쪽이 맞다.
무드는 예외로 얼굴형 선호 무드로 채운다 — RAG 가 얼굴형별로 이미 정의해 둔 값이라 창작이 아니고,
UI 가 3개를 전제하기 때문이다.

### 4. UI 가 0~3개를 정직하게 표현하게 한다

`AnalysisResult` 는 `features` 가 비면 `['균형잡힌 비율', '입체적인 골격', '부드러운 눈매']` 를
**분석 결과처럼** 보여주고 있었다 (이 ADR 과 무관하게 이미 있던 버그다). 더미를 제거하고 개수에 맞춰
제목을 바꾸며, 0개면 "뚜렷하게 두드러지는 특징 없이 전체적으로 균형 잡힌 얼굴이에요" 를 보여준다.

### 5. `tools/eval.py` 의 프롬프트 사본을 없앤다

회귀 도구가 `ANALYZE_PROMPT` 사본을 들고 있었고, 그 사본은 실사 판별 조건·무드 필드·옆선 직선성
기준이 빠진 옛 버전에 멈춰 있었다. **골든셋 회귀가 운영과 다른 프롬프트를 재고 있었다는 뜻이다.**
`backend/services/rag_service.py` 에서 직접 import 하도록 바꿔 구조적으로 어긋날 수 없게 했다.

## 근거

- 모순된 결과는 분석 신뢰도를 직접 깎는다. "둥근형"이라 해놓고 "각진 턱선을 감싸준다"고 조언하면
  사용자는 분석 전체를 의심한다.
- 무드 제약은 이미 데이터에 있었다. 새 판단 기준을 발명한 게 아니라 **있는 데이터를 실제로 쓰게** 했다.
- 필터를 삭제 전용으로 두면 결과가 빈약해진다는 우려가 있었다. 그래서 프롬프트가 다른 축에서 채우고,
  그래도 모자라면 UI 가 솔직하게 적게 보여주는 3단 구조로 갔다.

## 영향

| 대상 | 변경 |
|------|------|
| `backend/data/face-hair.json` | `moodBanned` 7개 얼굴형에 추가 |
| `backend/services/rag_service.py` | 정합성 상수 · 무드 룩업 · `sanitize_analysis` · 프롬프트 규칙 |
| `backend/services/gemini_service.py` | 카드 프롬프트 정합성 규칙 · 허용 무드 주입 · sanitize 연결 |
| `src/components/AnalysisResult.jsx` | 더미 features 제거, 0~3개 렌더 |
| `tools/eval.py` | 프롬프트 사본 제거 → 백엔드 import |
| `backend/test_consistency.py` | 신규 — 정합성 회귀 15케이스 |

`ANALYZE_PROMPT` 를 건드렸으므로 **`/eval-face` 골든셋 회귀가 필요하다.** 얼굴형 판정 분포가
바뀔 수 있다 — 특히 "사각턱이 보이면 얼굴형을 재검토하라"는 지시가 사각형 판정을 늘릴 수 있다.

## 골든셋 회귀 (2026-08-19)

`/eval-face` 9장 결과: **정확도 5/9 (55.6%) · 정합성 위반 0건.**
결과 원본은 `tools/eval-claude-results-2026-08-19.json`.

정확도가 2026-05-31 기록(9/9)보다 낮다. **이 변경이 유발한 회귀는 아니다** — 오판한 3장을
변경 전(HEAD) 프롬프트로 재평가했더니 세 장 모두 동일하게 오판했고, 평가 방식(프롬프트를
인라인으로 주는지 파일로 주는지)도 1장 교차 확인했으나 결과가 같았다. 남는 설명은 평가 모델
버전 차이다 (2026-05 기록은 `claude-sonnet-4-6`).

이 ADR 이 목표한 지표인 정합성 위반은 9장 전부 0건이다 — 얼굴형과 어긋나는 feature 도,
금지 무드도 나오지 않았다. 무드는 9장 모두 "선호 2개 + 나머지 1개" 규칙을 지켰다.

부수 관찰: 9장 중 3장이 `features` 빈 배열이었다. 예전 UI 였다면 이 3장이 하드코딩 더미
3개를 분석 결과처럼 보여줬을 것이다.

**얼굴형 판정 정확도 자체는 별도 과제로 남는다.** 오판 4장을 추적한 결과는
`tools/eval-analysis-2026-08-19.json` 에 있고, 요약하면 세 층이다.

1. **출력 형식이 가장 큰 요인.** 같은 사진·같은 프롬프트에서 응답에 근거 서술을 요구했더니
   2장(지젤·천우희)이 오답 → 정답으로 뒤집혔다 (5/9 → 7/9). JSON-only 출력이 분류 우선순위
   4단계를 실제로 밟지 않고 인상으로 즉답하게 만든다. **운영도 `responseMimeType=application/json`
   이라 같은 문제를 안고 있다.**
2. **사진에서 판정 근거를 볼 수 없다.** 오판 4장 전부 머리카락이 gonial 과 옆선을 가려,
   분류 우선순위 1번(옆선 직선성)을 관찰할 수 없었다고 답했다. 확신도는 4장 모두 55~62 로
   "판정 어려움" 임계(80%)에 미달인데도 확정 판정이 나왔다. 1~3단계가 근거 부족으로 배제되면
   4단계의 계란형이 사실상 기본값으로 작동한다.
3. **MediaPipe 수치는 변별력이 없고 일부는 오판을 강화한다.** 9장의 변동계수가 2~3%에 그친다.
   특히 긴형 기준인 `aspectRatio 1.4 이상`은 9장 최대가 1.234 라 **도달 불가능한 임계값**이다.
   정채연에 수치를 주자 모델이 `jawAngle 140.65` 를 "각짐과 거리가 멀다"고 읽어 사각형을 배제했는데,
   정작 사각형 정답인 정유미는 143.97 로 더 완만하다 — 프롬프트에 임계값이 없어 자의적으로 해석된다.

## 남은 것

- ~~응답 스키마에 근거 필드 추가 검토~~ → **적용함** (아래 "후속: 판정 근거 필드" 참조).
- **`jawAngle` · `aspectRatio` 임계값** — 재정의하지 않기로 했다. 임계값 문제가 아니라 지표가
  얼굴형과 상관이 없다는 것이 골든셋 9장 분석 결론이다. 상세는 `tools/eval-analysis-2026-08-19.json`
  의 `지표정밀분석`. 프롬프트의 1순위 기준은 "옆선의 직선성"인데 10개 지표 중 그것을 재는 것이 없다.
  **도달 불가능했던 `aspectRatio 1.4` 기준은 제거했다** (실측 최대 1.234 — 항상 참인 배제 조건이라
  긴형 판정을 원천 차단하고 있었다). `test_consistency.py` 가 재유입을 막는다.

  옆선 직선성 지표를 새로 만들려는 시도와, 지금 도구에서 정보를 더 뽑으려는 시도를 각각 세 가지씩
  해봤고 전부 실패했다 (`tools/eval-analysis-2026-08-19.json`). 요지는 두 가지다.
  - MediaPipe FaceMesh 는 평균 얼굴 메쉬를 사진에 맞춰 변형하는 모델이라 골격 개인차가 평균으로
    회귀한다. 계란형과 사각형의 gonial 위치 차이가 광대폭의 0.5% 다. 어떤 지표를 얹어도 갈리지 않는다.
  - z 좌표 사용·고개 각도 보정·얼굴 크롭 확대 모두 판별을 개선하지 못했다. **문제는 정보량이 아니라
    "그 사진에서는 볼 수 없다"는 것이다** — 오판 사진들은 머리카락이 턱선을 덮고 있다.

  고개 각도 보정은 노이즈를 32% 줄였으므로, features 판정(눈 간격·이마 폭) 신뢰도가 문제될 때
  재검토할 가치가 있다. 얼굴형 판별용으로는 채택하지 않는다.
- **"판정 어려움" 임계 — 관측만 하기로 했다 (선택지 C).** `confidence` 로 자동 분기하지 않는다.
  골든셋 관측치가 55~65 에 몰려 있어 80 기준을 강제하면 사실상 모든 사용자가 "판정 어려움"을 받는다.
  `sanitize_analysis` 가 `confidence` 와 관찰 불가 항목을 stderr 로 남기므로, 운영 분포를 본 뒤 정한다.
- **재촬영 안내 (선택지 D) — 골든셋 확대 후 진행.** step1~3 중 2개 이상이 "관찰 불가"면
  "머리를 귀 뒤로 넘기고 다시 찍어주세요" 같은 안내를 띄운다. 오판 원인이 머리카락 가림이었으므로
  원인을 직접 겨냥한다. `confidence`(모델의 주관)보다 객관적이다. UI 흐름 추가라 `docs/ui-flow.md`
  갱신이 따라온다. **골든셋이 늘어나 판단 근거가 쌓인 뒤 착수한다.**
- 골든셋 사진 확대 — 진행 예정. 턱선이 보이지 않는 사진이 다수라 평가가 사진 한계에 갇혀 있다.

## 후속: 판정 근거 필드 (2026-08-19)

위 원인 1번에 대응해 `faceTypeReason` 을 응답 스키마에 추가했다.

```json
"faceTypeReason": {
  "step1_sideLine": "곡선 — 광대 아래 옆선이 완만하게 이어짐",
  "step2_cheekbone": "아님 — 이마·턱과 폭 차이가 크지 않음",
  "step3_vertical": "약 1.15 — 1.4 미만",
  "decidedAt": 4,
  "confidence": 78
}
```

**핵심은 필드 순서다.** 출력 스키마에서 `faceTypeReason` 을 `faceType` **앞에** 두어, 모델이
결론을 먼저 뱉고 근거를 끼워 맞추는 것을 막는다. step1~3 은 분류 우선순위 1·2·3번 검사에
그대로 대응하고, 머리카락·손·각도로 볼 수 없으면 `"관찰 불가"` 를 쓰게 했다.

진단용이므로 **UI 에 노출하지 않고 DB 에도 저장하지 않는다.** `sanitize_analysis` 는 이 필드를
보존하고, `confidence` 와 관찰 불가 항목을 stderr 로그로 남긴다 — 낮은 확신도에서 확정 판정이
나오는 빈도를 운영에서 관측하기 위해서다. 임계 처리는 아직 넣지 않았다.
- `tools/eval.py` (Gemini 종량제) 로 운영 모델 기준 정확도 재측정. Claude 평가는 sanity check 이지
  운영 정확도가 아니다.
- `diamond` 의 선호 무드에 `SHARP` 가 있다. 골격은 부드럽지만 광대가 도드라져 인상이 강한 형이라
  의도된 값으로 두었다. 무드는 골격 규칙으로 유도하지 않고 데이터를 단일 소스로 삼는다.

## 후속: features 판단 순서 · 관찰 불가 기준 (2026-09-15)

`/eval-face` 에 features 축을 추가하고(`tools/score_features.py`) 9장 × **3회** 반복으로 재측정했다.
1회 측정으로는 보이지 않던 것이 드러났다. 원본은 `tools/eval-claude-results-2026-09-15.json`(v1) 과
`tools/eval-claude-results-2026-09-15-v2.json`(v2).

### 무엇이 보였나 (v1 = 이 ADR 적용본, 27회)

- **features 안정성 Jaccard 0.37.** 9장 중 6장은 3회에 공통으로 나온 라벨이 0개다. 한 장은 0.00 —
  회차마다 완전히 다른 답이 나온다. 단 **반대 속성 충돌은 0건**이라 모순이 아니라 *매번 다른 부위를
  집는* 문제다. 프롬프트가 라벨 목록만 주고 **어떤 순서로 무엇을 보라는 기준을 주지 않았기 때문이다.**
- 수율 1.0개(목표 3) · 0개 6/27 · 커버리지 6/37. `아몬드 눈` 에 편중된다.
- 정합성·어휘 위반 0/27 — 이 ADR 의 규칙은 3회 반복에서도 유지된다.
- **`confidence` 27회 전부 80 미달(55~75, 평균 64.7)인데 `판정 어려움` 은 0건.**
  위 "남은 것" 의 선택지 C 판단(자동 강등 불가)이 재확인됐다.
- **"관찰 불가" 신고가 27회 전부 0건이었다.** 모델은 *"머리카락이 턱선을 가리지만"* 이라고 서술하면서
  값은 `곡선` 으로 확정한다. 즉 선택지 D(관찰 불가 2개 이상 → 재촬영 안내)는 **트리거가 죽어 있어
  그대로 켜도 발동하지 않는다.** 이것이 이번에 새로 알게 된 사실이다.

### 무엇을 했나 (v2)

`ANALYZE_PROMPT` 만 수정했다 (5837자 → 7995자). 코드 동작 변경 없음.

1. **features 판단 순서 고정** — 눈 → 코 → 입술·인중 → 윤곽 여백. 부위별 최대 1개, 3개 차면 정지.
2. **라벨별 관찰 기준** — "가로:세로 3:1 이상이면 긴 눈", "두 눈 사이 거리를 한쪽 눈 가로폭과 비교" 처럼
   비교 대상을 명시. 얼굴형이 4단계 우선순위로 안정된 것과 같은 원리를 features 에 적용했다.
3. **정면 사진으로 판정 불가한 라벨 명시** — `목 짧음`·`콘헤드`·`어깨 너비 넓음`·`승모근 발달` 은
   얼굴만 나온 사진에서 넣지 않는다. 목록에서 삭제하지는 않았다 (전신 사진이 들어올 여지를 남긴다).
4. **"관찰 불가" 판단 기준** — 머리카락이 gonial·옆선을 덮으면 `step1` 은 관찰 불가.
   앞머리가 헤어라인을 덮으면 `step2` 도 관찰 불가. **"가려져 있지만 ~로 보인다" 는 관찰 불가다.**

### 남는 문제 — 판정 어려움이 에러 화면으로 간다

`App.jsx` 는 `faceType === '판정 어려움'` 을 `error_face` 로 보낸다. v2 에서는 이 값이 6/27 회차,
한 사진(땅콩형 #2)은 **3회 모두** 판정 어려움이다. 그 사진을 올린 사용자는 항상 에러를 본다.
정직해진 판정이 UX 후퇴로 보이는 구간이다.

그래서 **선택지 D(재촬영 안내)의 필요성이 커졌고, 이제 트리거도 살아 있다.** 착수 조건이었던
"골든셋 확대" 와 별개로, 안내 문구를 원인에 맞게 바꾸는 것(현재 "얼굴 윤곽이 잘 보이는 정면 사진으로"
→ "머리를 귀 뒤로 넘기고")은 먼저 할 수 있다. UI 흐름 변경이라 `docs/ui-flow.md` 갱신이 따라온다.

features 안정성 0.488 도 여전히 절반이다. 다음 후보는 `아몬드 눈` 편중과 눈 모양 3분류
(긴/아몬드/둥근)의 경계 기준이다.
