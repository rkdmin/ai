01 / 방향과 변경 규모

단순한 화면 개편보다 범위가 큽니다

현재 앱의 중심은 얼굴형 분석 → 헤어 또는 메이크업 카드 생성 → 카드 상세 → 사진 합성·공유입니다. 최신 와이어프레임은 여기에 대표 Beauty Profile, 통합 유료 리포트, 무료 개인화 콘텐츠, 친구 초대와 랭킹, 구매 복원과 계정 동기화를 더합니다.

유료 리포트한 번 구매 → Hair + Makeup → 상세 가이드·저장·공유

분류무엇을 뜻하나대표 작업
새 기능현재 없는 행동·저장·권한·외부 연동게스트 프로필 유지, 결제·구매 복원, 콘텐츠 피드, 저장한 스타일, Room·초대·랭킹
데이터 변경기존 값으로 새 화면을 정확히 채울 수 없는 경우Primary + Traits, 판단 근거와 확신도, 리포트 공통 요약, 기장·볼륨·미용실 가이드, 콘텐츠·제품 사전
UI·UX 변경이미 있는 데이터를 표현하거나 기존 행동을 배치하는 작업가이드 화면 배치, 헤더·탭바, 상세 레이아웃, 저장·공유 버튼, 시트와 빈 상태
결정 필요와이어프레임만으로 정책을 확정할 수 없는 경우재분석 후 구매 범위, Traits 사전, 가격, 결제 플랫폼, 복원 소유권, 케미 계산 규칙

한 화면에 여러 분류가 함께 들어갑니다. 예를 들어 MY의 카드 모양은 UI 작업이지만, 게스트 결과를 다시 여는 동작은 새 기능이고, 무드 요약을 저장하는 일은 데이터 변경입니다.

현재 코드에서 확인한 중요한 출발점

  • 카드 잠금은 현재 모두 해제됩니다. App에는 광고 분기가 있지만 카드 매퍼는 locked: false를 반환합니다. 1·2·3위 무료/유료 잠금이 이미 완성됐다고 가정하지 않습니다.
  • 분석 결과는 실행 중 React 상태에 있습니다. 게스트 플래그 저장과 별개로, 프로필·분석·구매·Room을 지속 보관하는 체계는 없습니다.
  • 저장된 분석에서 무드가 복원되지 않습니다. 분석 테이블에는 무드 컬럼이 없고, 상세 조회는 빈 무드 배열을 반환합니다. 새 MY와 FOR YOU를 만들기 전에 해결해야 합니다.
  • 결제·구매 복원·친구 케미·콘텐츠 피드는 없습니다. 기존 히스토리·인증·공유 기반을 활용하되 기능 자체는 새로 개발해야 합니다.
  • 사진 보관 안내와 구현이 다릅니다. 업로드 동의는 즉시 폐기를 안내하지만 로그인 분석 코드는 90일 만료 시각을 저장합니다. 만료 시각 기록과 실제 파일 삭제도 별개입니다.
02 / 기준과 확인 범위

어떤 근거로 계획했는지

근거확인한 내용계획에 반영한 방식
최신 캔버스 실제 텍스트핵심 분석·무료 결과·결제·유료 리포트·헤어/메이크업 상세·최종 IA 규칙화면별 실제 문구와 상품·탭·게스트 정책을 직접 대조
전체 페이지 레이어 메타데이터최신 캔버스 내 54개 화면 크기 프레임: 표시 52개, 숨김 중복 2개표시된 모든 프레임을 인덱스로 기록. 숨긴 ARCHIVE_DUPLICATE는 구현 대상 제외
캔버스 캡처4개 큰 구역, 화면 배치와 흐름 연결배치 확인용. 캡처만으로 동작·정책을 추정하지 않음
현재 소스와 문서App 상태·이동, API 매퍼, 분석·카드·사진·히스토리, Auth·공유, SQL·RAG·기존 결정실제로 있는 기능과 문서에만 적힌 계획을 구별

확인 한계: 추가 조회 중 Figma MCP가 사용 한도 오류를 반환했습니다. 핵심 구역 외 STYLE·MY·CHEMISTRY는 확보한 레이어 구조와 레이어 이름을 사용했습니다. 레이어 이름은 현재 화면 문구와 다를 수 있습니다. 특히 초대 웹 화면은 main-title 같은 이름만 확보되어 실제 카피·정확한 CTA 목적지·세부 주석은 착수 전에 재확인해야 합니다.

52개 표시 프레임은 52개 독립 페이지를 뜻하지 않습니다. 긴 버전의 홈·무료 결과, 중복 제품 목록, 복원 상태 5종을 포함합니다. 동일 역할의 화면은 공통 컴포넌트와 상태로 묶는 제안입니다.

피그마에서 확인한 기준

  • 메인 탭은 홈 / 스타일 / 케미 / 마이. 분석·결과·결제·상세·초대 웹 흐름에서는 하단 탭을 숨깁니다.
  • Beauty Report 1회 구매로 Hair와 Makeup을 함께 해제합니다. 두 화면은 같은 리포트의 탭입니다.
  • STYLE은 결제로 잠그지 않습니다. 분석 전에는 에디토리얼, 분석 후에는 FOR YOU 개인화를 제공합니다.
  • Guest-first로 시작하고 저장·복원·Room 영구화 시 계정 연결을 안내합니다.
  • MY에서 구매한 리포트 진입은 기본 Hair 탭, 뒤로가기는 MY로 돌아옵니다. MVP는 사용자당 통합 리포트 1개라는 주석이 있으나 재분석과의 관계는 미확정입니다.

F02. Guest-first Beauty Profile

기존 기반: AuthContext·게스트 플래그·히스토리 / 신규 프로필 지속 보관 필요

개발할 것
초기 진입은 로그인 없이 홈으로 보냅니다. 현재 분석을 가리키는 Beauty Profile과 분석 이력을 분리하고, 게스트 결과·북마크를 기기에 보관합니다. 원본 사진 전체를 localStorage에 넣는 방식은 피하고, 결과 JSON과 미디어 보관을 분리합니다. 계정 연결 후에는 서버 저장본과 실제로 병합합니다.
중요한 설계
게스트 체험 플래그 ≠ 서버에서 소유권을 증명하는 신원입니다. 구매와 Room은 서버가 검증 가능한 principal 또는 제한된 capability가 필요합니다. Supabase 익명 세션 후 연결 방식과 별도 게스트 세션을 비교합니다. 기존 isAuthenticated에 익명 JWT를 그대로 넣으면 MY·히스토리 gate 의미가 바뀌므로 “연결 계정 여부”와 “서버 principal 존재”를 구분해야 합니다.
완료 기준
분석 후 앱/브라우저를 다시 열어도 홈·MY·FOR YOU가 같은 결과를 보여줍니다. 계정 연결 재시도는 중복 분석을 만들지 않습니다. 계정을 바꾸면 이전 계정 데이터가 노출되지 않습니다.

F03. 사진 확인과 분석 오류 분리

기존 기반: 파일 크기·형식 검사, MediaPipe 미검출 거부, 네이티브 입력

개발할 것
선택 사진 확인 화면의 검사 결과를 데이터로 제공합니다. 서버의 가벼운 검증 경로에서 얼굴 수·기본 해상도·검출 여부를 확인하고, 자세한 윤곽/정면/가림 판정은 구현 가능한 기준을 별도 정의합니다. 첫 검증 뒤 분석 요청에서 동일 이미지 결과를 재사용할 수 있도록 임시 이미지 ID·검사 ID를 고려합니다. 다중 얼굴을 판별하려면 현재 최대 1명 설정을 확장해야 합니다.
오류 계약
NO_FACE, MULTIPLE_FACES, INVALID_IMAGE, LOW_QUALITY, ANALYSIS_UNCERTAIN, RATE_LIMITED, NETWORK_ERROR 등 원인별 코드를 제안합니다. 기기 권한 거절·사용자 취소는 서버 오류와 분리합니다. 확신 없는 “윤곽 확인 완료” 체크는 노출하지 않습니다.
완료 기준
얼굴 없음/여러 얼굴은 불필요한 Gemini 호출 전에 걸러집니다. 검증 실패·파일 재선택·취소·권한 복귀가 모두 동작합니다. 사전검사의 처리·전송 목적도 동의 문구와 일치합니다.

기존 API

추천안은 구매 검증 후 생성, 동일 리포트 재조회는 저장본을 반환하는 방식입니다. 구매 직후 생성 실패는 재결제가 아니라 리포트 생성 재시도로 처리합니다. 빠른 준비가 필요하면 결제 전 전체 생성과의 비용·대기시간을 비교하되 무료 사용자 전원 생성은 별도 선택입니다.
완료 기준

F05. 결제·구매 내역·구매 복원

기존 기반 없음 / 가장 먼저 플랫폼 검증이 필요한 외부 연동

개발할 것
상품·실제 가격 조회, 구매 요청, 서버 검증, 권한 발급, 거래 저장, 구매 복원, 취소/환불 후 권한 갱신을 개발합니다. 결제 transaction과 앱 entitlement를 분리하고, 같은 거래 token은 한 번만 등록합니다. 가격과 거래 상태는 클라이언트 입력을 신뢰하지 않습니다.
플랫폼 제안
기존 Android 우선 전략을 유지한다면 Play Billing 연동을 먼저 시제품으로 검증합니다. “사용자당 리포트 1개를 지속 재열람” 정책이면 비소모성 1회 상품이 후보입니다. “분석마다 재구매”라면 소비·복원·리포트 소유 정책을 다시 설계해야 합니다. 웹은 데모 접근과 실제 결제를 구분하고 웹 결제는 별도 범위로 결정합니다.
필수 예외
사용자 취소, 결제 pending, 스토어 성공 후 서버 검증 지연, 앱 종료 후 복귀, 중복 callback, 기존 구매, 다른 앱 계정으로 복원, 환불/취소 통지, 네트워크 끊김을 처리합니다. 스토어 성공과 콘텐츠 생성 완료를 하나의 상태로 뭉치지 않습니다.
복원의 의미
스토어 구매 확인만으로 원본 분석과 생성 리포트가 복원되지는 않습니다. 거래↔앱 소유자↔리포트 ID 매핑이 서버에 남아 있어야 합니다. 현재 분석이 없어도 기존 리포트를 되찾을 수 있어야 합니다. 구매 계정이 달라졌을 때 자동 이전 여부는 결정이 필요합니다.
완료 기준
스토어 sandbox에서 실제 구매·대기·복원·중복·환불 시나리오를 통과하고, 임의 클라이언트 성공값으로 권한을 얻을 수 없습니다. 전체 생성 실패 시 복구 경로가 있고 재결제 버튼을 강요하지 않습니다.

서버 검증·acknowledgement 권고와 pending 처리는 Google Play 보안 가이드와 Billing 통합 문서를 참고했습니다. 통지 수신 후 실제 상태 재조회는 RTDN 문서에 근거합니다. 사용할 SDK·버전·출시 시점 정책은 착수 때 재확인합니다.

F06. TRY ON과 저장·공유 동작 재정의

기존 기반: 사진 생성·html2canvas·Filesystem·Share / 그대로 재사용할 부분이 많음

개발할 것
헤어 상세의 TRY ON은 구매/계정/사용량 정책에 따라 접근합니다. 지금 합성 전에 타는 광고 mock 흐름은 새 상품 정책과 맞게 정리합니다. 사진 만료, 생성 중, 생성 실패, 한도 초과, 기존 결과 재열람을 독립 상태로 둡니다.
캐시 주의
현재 서버는 분석+카드 종류로 한 사진만 캐시합니다. 헤어 추천 3개 모두에서 TRY ON을 누를 수 있게 만들면 다른 스타일에도 첫 합성 사진이 재사용될 수 있습니다. “대표 스타일 1개만 지원” 또는 “안정적 추천 ID별 캐시·사용량” 중 선택해야 합니다. 또한 캐시 조회보다 rate limit 차감이 먼저인 현재 순서도 점검합니다.
사용량·동시성
구매 권한과 AI 생성 한도는 별개입니다. 구매 게스트도 검증 가능한 소유자 기준으로 한도를 적용하고, 생성 예약·차감은 재시작/여러 서버에서도 유지되는 원자적 저장을 후보로 검토합니다. 같은 요청의 재시도·중복 탭은 하나의 생성 작업으로 합치고, 캐시 조회·실패 작업의 차감/환급 규칙을 정합니다. 현재 인메모리 IP 제한만으로 유료 생성 비용을 통제한다고 가정하지 않습니다.
저장 구분
리포트 저장, 스타일 북마크, 이미지 기기 다운로드는 서로 다른 행동입니다. 버튼의 저장 대상과 저장 위치를 명확히 정합니다. 공유는 전체 긴 리포트 이미지보다 선택한 요약/미용실 가이드 등 유용한 단위부터 제공합니다. 메이크업 TRY ON은 추가하지 않습니다.
완료 기준
다른 추천의 합성 결과가 섞이지 않고, 캐시 재열람은 새로운 생성으로 계산되지 않습니다. 저장한 스타일 화면은 이미지 다운로드와 구별됩니다. 웹과 네이티브의 저장·공유가 모두 동작합니다.

콘텐츠 피드, 카테고리/무드별 목록, 기사 상세, 관련 콘텐츠·제품, 분석 후 FOR YOU를 만듭니다. 첫 버전은 운영자가 검토한 정적 JSON·정적 미디어 + 서버 조회로 시작하는 제안입니다. CMS나 자동 수집은 필수 선행 작업으로 두지 않습니다.
개인화
대표 무드와 Traits, 얼굴 구조의 검증 가능한 태그로 점수를 계산하고 매칭 이유를 반환합니다. 기사별 무드 활용법과 CONTRAST/TEXTURE/POINT를 사전에 작성하면 매번 AI를 호출하지 않아도 됩니다. 데이터가 부족하면 인기/에디토리얼로 폴백하고 개인화됐다고 과장하지 않습니다.
미확정 화면
“더 보기” CTA는 여러 개 있지만 별도 목록 프레임이 없습니다. 카테고리·무드 필터가 있는 공통 목록 화면을 추가하는 제안입니다. “지금 많이 보는”은 실제 집계가 없으면 “에디터 추천” 등 데이터 근거와 맞는 문구로 바꿉니다.
완료 기준
분석 전에도 글을 읽고, 미구매 상태에서도 FOR YOU를 씁니다. 모든 카드와 더 보기의 목적지가 있습니다. 실제 콘텐츠·미디어·제품 링크가 연결되고 초안/TBD가 제품 화면에 나오지 않습니다.

F08. Beauty Room·친구 참여·케미 랭킹

기존 기반 없음 / 새 제품 기능과 계산 규칙

개발할 것
Room 생성·조회, 방장 프로필 snapshot, 초대 token, 친구 참여, 두 프로필 조합 평가, 현재 랭킹을 만듭니다. 한 사용자 1개 활성 Room을 MVP 후보로 두고, 친구 0명과 1명 이상 상태를 구분합니다.
계산 제안
모델의 자유 점수 생성보다 버전이 있는 조합 표·Traits 호환 규칙으로 재현 가능한 결과를 만드는 제안입니다. 타입 이름과 설명 문장은 운영자가 검토합니다. “케미”는 사진 속 인상 조합을 즐기는 표현으로 관리하고 외모 가치·실제 관계 적합성을 단정하지 않습니다. 공식 계산식은 아직 없습니다.
데이터 규칙
자기 참여 방지, 동일 친구 중복 참여 방지, 재분석 후 update 여부, 동점 규칙, 친구 삭제·방장 삭제·초대 회수, 참여 수 집계, 새 참여 후 갱신 방법을 정의합니다. 처음은 재진입/수동 새로고침부터 시작하고 실시간 subscription은 필요성을 검증합니다.
공개 범위
초대 링크는 방장·친구의 이메일이나 원본 사진 열람 권한이 아닙니다. 공개용 DTO에 닉네임·대표 무드·선택된 조합 요약만 넣고 전체 이력·원본 사진·결제 정보는 제외합니다. 닉네임 수집과 참여 동의 화면은 추가 설계가 필요합니다.
완료 기준
같은 친구가 다시 참여해도 참여 수가 늘지 않고, 점수 계산이 재현됩니다. 링크 token을 바꿔 다른 Room의 비공개 데이터를 읽을 수 없습니다. 삭제·초대 회수 시 공개 조회도 즉시 제한됩니다.

F09. 초대 웹 흐름과 앱 인계

기존 입력·분석 UI 일부 활용 / 공개 주소·token·앱 링크는 신규

개발할 것
초대 주소로 들어오면 유효한 Room과 공개 방장 요약을 읽습니다. 친구는 기존 프로필 재사용 또는 새 분석 후 참여하고 웹에서 결과·현재 순위를 봅니다. 로그인/OAuth 이후에도 초대 맥락을 보존합니다. 웹 초대 흐름에는 앱 하단 Nav를 넣지 않습니다.
앱 인계
짧은 만료·1회 사용 token으로 서버의 프로필/참여 맥락을 넘기고, 앱은 검증 후 소유권을 획득합니다. URL에 원본 사진·전체 결과·이메일·세션 JWT를 넣지 않습니다. 설치된 앱 열기와 앱 미설치 후 설치 복원은 별도 문제입니다. 설치 후 자동 인계가 안 되는 경우 계정 연결 후 복원 또는 초대 링크 다시 열기를 MVP 폴백 후보로 둡니다.
완료 기준
설치됨/미설치, 새 프로필/기존 프로필, 로그인 취소, token 만료/재사용, 외부 브라우저·카카오 인앱 브라우저, 앱 콜드 시작/이미 실행 중을 확인합니다. 전달 중 오류 시 빈 스플래시에 머물지 않습니다.

설치된 앱의 검증된 링크 연결은 Android App Links와 웹사이트 연결 설정을 참고합니다. 설치 전후 자동 복원을 이 문서만으로 보장하지 않습니다.

F10. 저장한 스타일과 조회 집계

기존 기반 없음 / 카드 공유의 “SAVE IMAGE”와 다른 기능

개발할 것
안정적 콘텐츠 ID로 저장·해제, 저장 목록, 전체/MAKEUP/HAIR 필터, 실제 개수 표시를 만듭니다. 게스트는 기기에 저장하고 계정 연결 시 중복 없이 합칩니다. 삭제/비공개된 기사, 깨진 이미지, 목록 없음과 동기화 실패를 처리합니다.
범위 선택

완료 기준
저장 상태가 목록·상세·MY 개수에 일치하고 계정 연결 재시도로 중복되지 않습니다. 비공개 콘텐츠는 저장본을 통해 우회 열람되지 않습니다.

F11. 계정 연결·동기화·로그아웃

개발할 것
연결 계정 상태, 로그인 방식·이메일, 각 데이터의 실제 동기화 상태, 마지막 오류와 재시도를 제공합니다. 프로필·이력·북마크·Room·구매를 같은 소유자 기준으로 병합합니다. “동기화됨”은 서버 저장 성공을 확인한 뒤에만 표시합니다.
충돌 처리
기존 계정 프로필과 기기 프로필이 다르면 어느 것을 현재로 사용할지 정합니다. 기존 구매·Room을 조용히 덮어쓰지 않습니다. 병합에는 재요청 가능한 작업 ID와 중복 방지 규칙을 둡니다. OAuth 취소·세션 만료·앱 복귀도 원래 행동으로 돌아옵니다.
세션 기반
현재 브리지는 토큰 만료 시 저장 세션을 지우며, refresh token을 저장해도 갱신 호출은 없습니다. 장기 복원·동기화를 지원하려면 갱신/세션 복구를 보완하고 네이티브 callback·앱 링크와 같은 흐름에서 검증합니다. Apple 로그인은 피그마 예시만으로 추가 확정하지 않습니다.
완료 기준
기기에서 연결한 결과가 다른 기기에서 동일하게 복원되고, 로그아웃하면 계정 캐시가 정리됩니다. 로그인만 성공하고 데이터 이전이 실패한 경우를 구별할 수 있습니다.

개발할 것

미확정 메뉴
“로그인된 기기”, “알림 설정”은 전용 화면·세션 관리/알림 백엔드가 없습니다. 알림 전체 시스템과 기기별 강제 로그아웃은 범위를 별도로 승인받는 제안입니다. 출시본에서 무반응 메뉴를 두지 않고 연결·명확한 보류·숨김 중 결정합니다.
완료 기준
삭제 요청 alert만 띄우는 현재 방식 대신 실제 정리가 확인됩니다. 삭제 후 링크·앱 캐시에서 데이터가 남아 보이지 않고, 실패한 일부 파일 삭제는 재시도됩니다. 안내 문구와 구현 보관 정책이 일치합니다.

기존 데이터 이전

  1. 기존 분석·카드 원본을 보존합니다. schemaVersion이 없는 값은 legacy로 읽는 adapter를 두고 새 리포트와 구별합니다.
  2. 저장되지 않은 무드·Traits를 만들어 복원하지 않습니다. 예전 분석에는 얼굴형·features를 보여주고 새 무드 정보가 없음을 표현하거나 사용자 동의 후 재분석합니다.
  3. 기존 무료 카드가 새 유료 구매를 의미하지 않습니다. 이전 카드 접근을 유지할지, 새 리포트만 별도 구매할지는 명시적으로 결정합니다.
  4. 기록 10개 초과 삭제는 나중에 적용합니다. 먼저 조회·표시 정책을 바꾸고, 구매한 리포트의 기준 분석·Room snapshot을 지우지 않도록 보관 규칙을 만든 뒤 정리합니다.
  5. 기기 저장본과 서버 병합은 중복 방지와 복구를 포함합니다. 서버 성공을 확인한 뒤 로컬 임시본을 정리하고 실패 시 재시도합니다.

퍼스널컬러 처리

최신 핵심 분석 흐름에는 기존 PersonalColor 단계가 보이지 않습니다. 추천안은 무료 무드 분석에서 필수 단계를 빼고, 선택적으로 알고 있는 값을 리포트/설정에서 받을 수 있게 하는 것입니다. 값이 없으면 색상 단정 대신 위치·형태·제형 중심으로 제공합니다. 현재 eye 필드가 퍼스널컬러 없을 때 null이 되는 규칙과 새 “확실한 EYE 가이드”는 역할이 다르므로 색상과 눈매 기법을 분리해야 합니다.
