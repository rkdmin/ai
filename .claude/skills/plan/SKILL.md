# plan — 실행 계획 관리

## 목적

`docs/plans/` 는 **"무엇을 어떤 순서로 할 것인가"** 의 단일 출처다. 상세 체크리스트가 여기 있고,
살아 있는 문서다. 이 스킬은 그 문서를 만들고 갱신하는 절차다.

규약(번호·표기·frontmatter·status)은 [`docs/plans/README.md`](../../../docs/plans/README.md) 가
단일 소스다. **이 파일에 규약을 복사해 두지 마라** — 두 곳이 어긋난다. 작업 전에 그 파일을 읽어라.

## 경계 — 어디에 쓸 것인가

| 쓰려는 내용 | 가야 할 곳 |
|------------|-----------|
| 할 일 목록, 완료 여부 | `docs/plans/` (이 스킬) |
| 왜 그렇게 정했나 | `docs/decisions/` (ADR, append-only) |
| 전체가 어디까지 왔나 | `docs/ROADMAP.md` — plan 을 가리키기만 한다 |

계획을 세우다 **결정**이 나오면 (기술 선택, 범위 변경, 순서 번복) 그 결정은 ADR 로 남긴다.
plan 에는 실행 항목만 둔다.

## 절차

### A. 새 계획 만들기

1. `npm run plans:progress` 로 현재 번호를 확인한다. **다음 번호**를 쓴다 (재사용 금지).
2. `docs/plans/README.md` 의 frontmatter 규격대로 파일을 만든다. 파일명은 `NNNN-영문-슬러그.md`.
3. 본문 구조는 기존 plan 을 따른다 — `## 완료 기준` → `## 구현` → `## 사용자 직접 확인`.
   - **완료 기준은 반드시 검증 가능하게 쓴다.** "품질 개선" 말고 "골든셋 정확도 90% 이상".
   - 코드로 확인 못 하는 항목은 `## 사용자 직접 확인` 으로 분리한다.
4. `docs/plans/README.md` 인덱스 표에 한 줄 추가한다. (안 하면 `docs:check` 가 잡는다)
5. 근거가 된 결정이 있으면 frontmatter `adr` 에 번호를 넣는다. 없으면 `[]`.
6. Phase 단위 계획이면 `docs/ROADMAP.md` 의 표에도 링크를 추가한다.

### B. 진행 반영하기

1. **끝난 항목만 체크한다.** 코드·테스트로 확인한 것만. 확신이 없으면 그대로 둔다.
   근거가 있으면 항목 뒤에 남긴다 — `- [x] Rate limiting 적용 (test_integration.py 429 케이스)`.
2. **접은 항목은 지우지 말고 취소선 + 이유.** 규약은 `docs/plans/README.md` 참조.
   왜 안 하기로 했는지가 다음 사람에게 필요하다.
3. 남은 항목이 0개가 되면 `status` 를 `Done` 으로 바꾼다. (안 바꾸면 `docs:check` 가 잡는다)
4. `npm run plans:progress` 로 확인한다.

### C. 계획 접기

1. `status: Cancelled` 로 바꾸고, 본문 맨 위에 **왜 접었는지**를 적는다.
2. 파일과 번호는 남긴다. 삭제하지 않는다.
3. 접은 이유가 결정 수준이면 ADR 도 함께 남긴다.

### D. 진행률 보기

```bash
npm run plans:progress
```

plan 별 체크 현황과 규율 위반을 출력한다. `npm run docs:check` 도 같은 검사를 포함한다.

## 하지 말 것

- **확인하지 않은 항목을 체크하지 마라.** 가짜 진행률이 낡은 문서보다 나쁘다.
- **ADR 본문의 체크박스를 갱신하지 마라.** append-only 다. 그건 작성 당시 스냅샷이고,
  살아 있는 사본이 `docs/plans/` 에 있다.
- **ROADMAP 에 체크리스트를 복사하지 마라.** ROADMAP 은 plan 을 가리키기만 한다.
- **번호를 재사용하거나 파일을 지우지 마라.** 취소된 계획도 번호를 유지한다.
